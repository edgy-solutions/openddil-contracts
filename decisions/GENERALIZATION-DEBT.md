# Generalization-debt registry

**Single authoritative home for "what is currently hardcoded that the
framework says should be configurable."**

## Why this file exists

The same debt items had begun appearing in two ADRs' framework-vs-
instantiation tables (ADR-0032 and ADR-0033), in slightly different
words. That is the **two-truths pattern in documentation form** — the
same disease this project has killed on sight at the data layer (two
authz corpora), the read layer (two read paths), and the policy layer.
The fix shape is the one that works every time: **one authoritative
home, everything else points.**

It also fixes a real discovery problem: "which ADR holds the row about
the three fixed UI views?" had no answer without grepping. Now there is
one place to look.

## Rules

1. **New debt rows land here only.** ADRs cite a row by ID; they do not
   restate it. Effective immediately, regardless of how much migration
   has happened.
2. **Migrate opportunistically, not ceremonially.** An existing
   duplicated row moves here the next time its ADR is touched for
   another reason. No dedicated migration pass.
3. **A row is closed by the work that generalizes it**, and the closing
   change updates the row rather than deleting it — the record of what
   *was* hardcoded is useful.
4. **Status vocabulary — declared, and machine-checked.** The Status
   column is this register's status *token*; `check-decision-indexes.sh`
   compares it against `FOLLOW-UPS.md` by exact string, so the spelling
   matters:

   | token | meaning |
   |---|---|
   | `open` | outstanding |
   | `fixed YYYY-MM-DD` | resolved; **the date is required** |
   | `in-arc <arc>` | being addressed by scheduled work |
   | `parked <ref>` | deliberately not being worked |

   `fixed` requires a date because a resolution with no date reproduces
   the unrecoverable-tense problem the anchor rule exists to prevent — a
   later reader cannot tell whether it was fixed before or after the
   claim they are checking. Prose registers carry the same token on a
   `` `Status: …` `` line above each row's heading; here the column *is*
   the token, and adding a second one would be two truths.

   *Renamed 2026-08-15:* `closed` → `fixed <date>` to match the shared
   grammar. GD-09's `resolved (0.1.40)` became `fixed 2026-08-08`; the
   chart version it shipped in is still in the row text, where it belongs
   — a status token records **when**, the row records **what**.

| **GD-09** | **Root-tier edge identity is baked into the runtime-bundle image, so edge names are NOT deployment configuration despite ADR-0033 saying they are.** The bundle ships `redpanda-connect-edge-01/02/03.yaml` and a `restate-config.toml` whose `[[ingress.kafka-clusters]]` entries hardcode `openddil-edge-01/02/03` — *and* docker-compose broker hostnames (`redpanda-edge-01:9092`) rather than release-prefixed k8s service names. A deployment that names its edges anything else gets `cp: can't stat /bundle/demo/redpanda-connect-<edge>.yaml` on the bridge, and subscription creation fails with *"specified cluster in the source URI does not exist"*. **Discovered 2026-08-08** by deploying the sample overlay (edges `edge-northpoint`/`edge-capeverdant`) to a real cluster for the first time. Sharpest possible contrast: the **tier-node** components generate their config from templates and handled the renamed tiers without complaint; only the older root-tier pipeline, which copies pre-baked per-edge files, is name-coupled. **RESOLVED 2026-08-08 — generation is the mechanism, declaration is the contract.** Per-edge connect configs and the root `restate-config.toml` are now chart-generated from `.Values.edges` (chart 0.1.40); the bundle's baked copies are no longer read. The overlay DECLARES topology as data; the chart GENERATES runtime wiring from it. **Baked per-edge runtime files are not an overlay artifact class and must not become one** — that resolution was considered and rejected because it relocates the same name-coupling one layer up and blesses it as a contract, obliging every overlay author to ship N wiring files for N edges and to edit N files to rename one. Verified on a real cluster with edges named `edge-northpoint`/`edge-capeverdant`: 13 Restate subscriptions created against `kafka://openddil-edge-<name>/…`, both bridges active. **CORRECTION (same day, before the claim aged):** an initial version of this row said the baked configs' docker-compose hostnames could not resolve under Kubernetes, so the bridge "could not have worked in any helm deployment at any edge name." **That was wrong.** `infrastructure.yaml` and `hub.yaml` deliberately publish *unprefixed alias Services* (`redpanda-<edge>`, `redpanda-hq`, `toxiproxy`, `electric-sync`) precisely so compose-era baked configs keep resolving — a documented compatibility shim. Generating the config **removes a dependency on that shim** rather than repairing a break. What does survive: the baked configs never read the `${EDGE_BROKER}`/`${HQ_BROKER}` env the chart injected despite a comment claiming they did — cosmetic dead weight, but it is why the wiring looked parameterised while the real coupling was a filename. Deliberate step toward ADR-0033's endpoint where the root tier is just the node with no parent. | ADR-0033 | fixed 2026-08-08 |

| **GD-10** | **The capability-item shape is undeclared, so the canonical model is defined de facto by whichever deployment integrated first.** Silver's stated position is a canonical schema derived from open standards; the capability payload has no proto, is stored verbatim as JSONB, and its only contract is three consumer reads (`capability_id`, `ammo`, `store_location`). **Discovered 2026-08-09** by AUDIT-2026-08-09-schema-provenance, which found the fear it was commissioned to test (a source hierarchy mirrored under a generic name) does not apply — because *no declared shape exists at all*. Vocabulary is clean and no foreign naming appears; the problem is dependence, not contamination: **free from corruption is not free from definition**, and a second deployment would map to a shape reverse-engineered from consumer reads of the first. Dependence-by-vacuum fails silently, where a declared mirror at least fails loudly. **HARD PREREQUISITE of any munitions stockpile work** — counting and aggregation built on an unowned shape inherits and multiplies its fragility. Resolution: an open-standards-derived capability-item schema declared in Silver (J3.7 weapon status, DIS munition-supply, AFSim stores, S2000M where stockpile semantics land), with deployment feeds decomposed into it by mapping. Governing rule: **discovery is not derivation** — a feed's fields and the sample overlay's authored fiction are inputs to the *mapping*, never sources for the *model*. When the canonical shape lands, the sample overlay's authored wire-schema is re-derived as an instance of it rather than standing as a second independent definition. Design work fenced until scheduled; the sketch in the audit's §1 is the deliverable so far. **No munitions phase document exists in any OSS repo** — this row is the prerequisite's only durable home until one does. | ADR-0020 / AUDIT-2026-08-09 | open |

| **GD-11** | **Asset class is INFERRED from one feed's publishing behaviour rather than declared.** The classifier reads *"has a row in `asset_capability_state`"* as LAUNCHER and *"munition-candidate variant without one"* as MUNITION. That is not a fact about the domain — it is a fact about how one source publishes (*things that report loadouts are launchers*), and it fails silently and plausibly in ordinary cases: a launcher whose feed has not emitted a snapshot yet becomes MUNITION; a producer that publishes stores for all platforms makes everything a LAUNCHER; externally-magazined systems vary. Every failure yields *a* class, never `UNKNOWN` — silent-absence arriving in the ontology layer. **Sibling of GD-10, same disease one layer up:** absent a declared canonical property, the source's behaviour fills it de facto — there the payload *shape*, here the class *property*. Resolution: `asset_class` becomes a declared Silver field (`AssetIdentity` field 11, purely additive) with `UNKNOWN` as zero-value; overlays assign it per source via the ladder producer-declared → mapped-from-declared-attributes → deployment-specific *stated* rule → UNKNOWN; **the core never infers**. Checked 2026-08-11: DIS already declares this — entity *kind* separates Platform from Munition at the tuple's first field, so ladder step 2 is the normal case and the capability-emitter rule is a proprietary-feed exception; but the ontology recognises **zero `kind=2` entries** today, so the DIS path cannot classify munitions until extended (an ontology PR, per ADR-0016). Design and migration sketch in `DESIGN-2026-08-11-declared-asset-class.md`; **design-only, nothing built**. Sequence with GD-10 — one message family, one upstream conversation. | ADR-0016 / DESIGN-2026-08-11 | open |

| **GD-12** | **Absence conventions are load-bearing, per-field, and declared nowhere but in the consumer's own body.** proto3 gives OpenDDIL's scalars no `optional`, so absent and zero are identical on the wire; every consumer that wants to distinguish *"no data"* from *"a reading of zero"* must invent a sentinel from the fields it has. Fusion invented two, and they are not the same shape: `Quantity` is unset when **`not unit and value == 0.0`** (the empty unit string is the only discriminator available), while `ConsumableState` is not-evaluable when **`quantity_capacity == 0`**. Both are correct, both are load-bearing, and **neither is written anywhere except inside `_eval_fuel` and `_eval_ammo`**. A producer therefore has to rediscover each convention by reading Python — which is exactly how one gets defeated: `sim-a-mapping` set `Quantity.unit` unconditionally and made fusion's fuel check *unreachable*, so an asset with no fuel telemetry presented as an asset with an empty tank (`AUDIT-2026-08-11-fallback-honesty` F1, fixed `efef7a6`). **An absence convention known only to the consumer is a contract with one signatory.** **Sibling of GD-10 and GD-11 — the same disease at the third layer:** there the payload *shape* was undeclared and there the class *property*; here the *absence semantics* are, and in all three the vacuum is filled de facto by whoever integrated first. The fix that surfaced it also showed the trap: two `.or(0)` calls one line apart carried **opposite** semantics — one a confabulation, one the sentinel itself — so a mechanical sweep for "defaults" would have removed the wrong one. Resolution: state the absence convention per canonical field type in the contracts, next to the type rather than inside its readers, and derive the evaluators' checks from that statement; where a convention cannot be expressed at all (a bare `uint32` with a meaningful zero), the finding is that the *containing* level must carry it — a map key can be dropped where its scalars cannot. Scope not established: only fuel and consumables were read, and only far enough to establish F1; **the population of conventions is unknown**, which is itself the argument for the sweep. **Submessage addendum, 2026-08-15 (ADR-0038 C4(a)).** The row above is about *scalars*, where proto3 gives no presence tracking and consumers must invent sentinels. **Submessages have the opposite problem: presence IS tracked, and it is asserted by writing.** Setting any field on a submessage — even to its zero value — marks the parent's field PRESENT, so a converter that populates an all-default provenance stamp turns *absent* into *empty-but-present*. Two consequences, both live: byte-identical round-tripping breaks for every pre-existing row (caught by `test_round_trip_preserves_full_state`, which is what that assertion is for), and — the one that matters semantically — **an empty stamp asserts "stamped with nothing" where absence means "unstamped."** For provenance specifically those are opposite claims: the first says a producer ran and declared no producer, version, or basis; the second says nothing ran. Fix and honest encoding are the same move: skip the submessage entirely when there is no claim to carry, so absent stays absent. *The generalizable form:* for scalars the question is *"how do I say nothing?"*; for submessages it is *"how do I avoid accidentally saying something?"* — and the second is easier to get wrong because the mistake is made by code that looks exhaustive and careful. | ADR-0013 / AUDIT-2026-08-11 | open |

| **GD-13** | **The generated protobuf bindings are not a package, so every consumer invents its own way onto the path.** `openddil-contracts/gen/python` is committed but never installed: container images add it via PYTHONPATH at build time, and on a host nothing does. Each of the three Python services solved it differently and none of them by declaring a dependency — cm-service repeats two `sys.path.insert` calls at the top of *every test module*, while fusion and projector had **no mechanism at all**, so `from openddil.… import …` failed at COLLECTION and pytest aborted the entire run. That is not "tests failing": it is NO SIGNAL, and it is the condition that let a suite stay dead for over two months (**VE-8**, ADR-0037 §Named limits) — the defect was one illegal identifier, but the *exposure* was that nothing could have noticed. **Discovered 2026-08-15** while making the suites run; conftest path injection was added to fusion and projector as the unblocking fix, which is a third variant of the same workaround rather than a resolution. The generated code is a **contract artifact consumed across repository boundaries** — exactly the thing a package exists to be — and today its interface is a filesystem layout that every consumer restates. Resolution shapes, in preference order: (a) publish `gen/python` as an installable distribution (`pip install openddil-contracts-gen==<version>`), which also makes the proto version a *declared dependency* rather than a sibling-checkout assumption and lets a service pin the gencode it was built against; (b) an editable install wired by each repo's bootstrap; (c) keep path injection but declare it once per repo rather than per test module. Only (a) removes the workspace-layout assumption, which currently reaches into CI — the Python workflows must check out the sibling repo at a specific path or reproduce the collection failure they exist to catch. **Spans three repositories**, so the fix is a coordination, not an edit. **CI UNBLOCKED 2026-09-05, and the debt is unchanged.** Python checks had been RED in all three siblings since the workflow was written — two failing to COLLECT (`No module named 'openddil'`, which is no signal rather than a set of failures) and the third DEGRADING instead, storing enum integers and failing one test with `assert '2' == 'LIFECYCLE_ACTIVE'`, a result that reads like a real defect and is not. The workflows already checked contracts out as a sibling and named the step "supplies gen/python"; it does not, because `gen/` is gitignored there and built on demand, so the layout was right and the artifact absent — the same shape as UD-9 one repository over. Each workflow now GENERATES the bindings, after the install and pinned to the runtime the service itself pins: an earlier ordering pulled the newest grpcio-tools, the install then downgraded protobuf underneath it, and every import died on `gencode 7.35.1 runtime 6.33.6`. **The generated code and the runtime that loads it are one decision**, and the workflow was making them separately. Now 71 / 72 / 84 passing. **This is the workaround the row already names as option (c), reproduced three times — which IS the debt.** Option (a), publishing `gen/python` as an installable distribution, would delete all three copies and make the proto version a declared dependency instead of a build instruction. | ADR-0019 / VE-8 | open |

## Not tracked here

- **Product backlog** — features not yet built. This registry is only
  for cases where the framework has *stated* a general position and the
  implementation is narrower than the statement.
- **Bugs.** A defect is not generalization debt.
- **Fenced future arcs** (the process plane, the analytics engine, DDS
  egress). Those are scoped work with ADR homes, not debt — unless a
  specific hardcoding blocks them, in which case that hardcoding gets a
  row.
